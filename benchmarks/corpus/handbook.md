# Engineering Handbook

These conventions apply across this organisation's repositories. They are
enforced in review; where a rule and a reviewer disagree, the rule is the
default and the exception needs a reason recorded in the pull request.

## 1. Repository layout

Application code lives under `src/`, grouped by domain rather than by technical
layer. A domain owns its models, its queries and its HTTP handlers; a change to
one domain should not require editing another domain's files.

Shared code lives in `src/common/` and must not import from any domain. If
shared code needs domain knowledge, the dependency is pointing the wrong way and
the logic belongs in the domain instead.

Tests live beside the module they exercise. Integration tests that span domains
live in `test/integration/`. Fixtures are generated by factory functions rather
than checked in as static files, so that a schema change breaks the factory in
one place instead of breaking forty JSON files.

Scripts that are run by hand live in `scripts/` and must be idempotent. Anything
run on a schedule belongs in the job system, not in `scripts/`.

Generated files carry a header saying they are generated and naming the command
that produces them. Editing a generated file by hand is always a mistake, and
the header is what tells the next person that.

## 2. Environment and setup

The supported runtime versions are pinned in the toolchain config. Do not add
code that depends on a newer runtime than the pinned floor, even when the local
machine has it available — CI runs the floor, and a feature that works locally
and fails in CI wastes more time than it saves.

Local development uses containers for every stateful dependency. Do not install
databases directly on a development machine; version drift between developers is
a recurring source of "works on my machine" defects that take days to diagnose.

Secrets never appear in the repository, in shell history, or in a `.env` file
that is not gitignored. Configuration that is not secret belongs in committed
config so that behaviour is reviewable.

Setup must work from a fresh clone with one command. If setup requires a person
to read a wiki page, the setup is broken and the fix is a script, not a better
wiki page.

## 3. General code style

Write code that matches the style of the files around it. Consistency within a
file matters more than consistency with a personal preference.

Prefer small functions with descriptive names over long ones with comments
explaining their sections. A comment that says what the next ten lines do is
usually a function waiting to be extracted.

Every public function carries a docstring explaining what it returns, including
the empty and error cases. "Returns the user" is not sufficient; "returns the
user, or None when no user has that id" is.

Name booleans so that the affirmative case is true. `is_enabled` rather than
`is_not_disabled`. Negated names produce double negatives at call sites and the
resulting bugs are hard to see in review.

Avoid abbreviations in identifiers except for genuinely well-known ones. `req`
and `res` are fine; `usr_prf_mgr` is not.

Prefer early returns over deep conditional nesting. Three levels of indentation
is a soft limit; beyond that, extract.

Constants are defined at module level in upper case, near the top of the file,
not buried at the point of first use.

Type annotations are required on public interfaces. Internal helpers may omit
them where the types are obvious from context.

Do not leave commented-out code behind. Version control remembers it; the next
reader does not know whether it is a work in progress or a fossil.

Keep lines under 100 characters. Wrapping is mechanical; arguing about it in
review is not a good use of anyone's time.

Group imports as standard library, third party, then local, with a blank line
between groups.

Functions that mutate their arguments say so in the docstring. Silent mutation
of a caller's data is among the most expensive classes of bug to trace.

Avoid global mutable state. Module-level caches are the most common form of this
and the most common cause of tests that pass alone and fail in a suite.

## 4. Error handling

Error messages name the thing that failed and the value that caused it. "Invalid
input" costs an engineer an hour; "invalid currency code: 'US$'" costs a minute.

Do not catch exceptions you cannot do anything about. Catching broadly to log
and re-raise is acceptable; catching broadly to continue is not.

Exceptions crossing a module boundary should be the module's own exception
types, not the underlying library's. Leaking a database driver's exception into
an HTTP handler couples the two permanently.

Validation happens at the edge, once. Internal functions may assume their inputs
are valid, and should assert rather than re-validate.

Timeouts are set explicitly on every outbound call. A default of "wait forever"
is how one slow dependency takes down an entire service.

## 5. Data access

Queries live in the domain that owns the table. Cross-domain reads go through
the owning domain's interface rather than by querying its tables directly.

Every query that can return more than one row is paginated. Unbounded result
sets work fine until the day a customer has a hundred thousand of something.

Migrations run in a single transaction where the database supports it. A
migration that half-applies is worse than one that fails outright.

Indexes are added in the same migration as the query that needs them, and the
migration comments name that query. An index whose purpose nobody remembers will
never be safely removed.

Long-running migrations on large tables must be written to be resumable and must
not hold locks that block writes. Adding a column with a default on a large
table is the classic way to take an outage.

Connection pools are sized deliberately and documented. The default is almost
always wrong in one direction or the other.

Prefer explicit column lists over `SELECT *` in application code, so that adding
a column cannot silently change what the application receives.

## 6. API design

Endpoints are named for resources, not for actions. Prefer `POST /v1/refunds`
over `POST /v1/create-refund`.

Responses have a stable envelope. Adding a field is a compatible change;
renaming or removing one is not, and requires a new version.

Errors return a machine-readable code alongside the human-readable message.
Clients must never have to match on message text.

Pagination is cursor-based rather than offset-based for anything that can be
written while it is being read, because offsets skip and duplicate rows under
concurrent writes.

Idempotency keys are accepted on every non-idempotent endpoint. Clients retry;
this is not optional.

Rate limit responses include a `Retry-After` header. A client that does not know
when to retry will retry immediately and make things worse.

Deprecated endpoints keep working for at least two release cycles and emit a
deprecation header for the whole period.

## 7. Security

Authorisation is checked in the handler, not in the client, and not only in the
UI. Assume every endpoint will be called directly.

Authorisation checks are positive: establish that this actor may do this thing,
rather than checking for known-bad cases. Blocklists miss cases that allowlists
do not.

Never log personally identifying information. Log opaque identifiers and join
against them when investigating.

User-supplied values are never interpolated into SQL, shell commands, file
paths, or template strings. Use the parameterised form even when the input
"cannot" contain anything dangerous.

Uploaded files are treated as hostile: validate type by content rather than by
extension, store outside the web root, and serve from a separate origin.

Dependencies with known vulnerabilities are upgraded within one sprint of the
advisory, or the exposure is documented with a reason for the delay.

Cryptographic primitives are never implemented by hand. Use the platform
library, and if the platform library does not offer it, that is a signal to
reconsider the design.

Session tokens are rotated on privilege change. A token issued before an account
was granted admin must not carry admin rights.

## 8. Testing

Tests assert on behaviour and named values rather than on serialized output.
A test that fails and is fixed by regenerating its expectation was not testing
anything.

Every bug fix ships with a test that fails without the fix. This is the single
highest-value testing rule and the one most often skipped under time pressure.

Tests must not depend on execution order, wall-clock time, network access, or
the contents of a developer's machine. Freeze time explicitly where behaviour
depends on it.

A flaky test is fixed or deleted the day it is noticed. Quarantining it is how a
suite stops being trusted, and an untrusted suite is worth nothing.

Prefer a small number of integration tests over a large number of tests against
mocks. A mock encodes an assumption about a dependency, and that assumption
silently rots as the dependency changes.

Test names describe the scenario and the expectation, not the function under
test. `test_refund_fails_when_order_already_refunded` beats `test_refund_2`.

Coverage is measured and reported, and is a diagnostic rather than a target.
Chasing a coverage number produces tests that execute code without asserting
anything about it.

## 9. Observability

Structured logging only. A log line is a record with fields, not a sentence with
values glued into it, because nobody can query the second kind.

Every request carries a correlation identifier from the edge through every
downstream call, and every log line includes it.

Log levels mean something specific: `error` is something a human must look at,
`warn` is something that may become an error, `info` is a business event, and
`debug` is off in production.

Metrics are named consistently and carry bounded label sets. An unbounded label —
a user id, a URL path with identifiers in it — will eventually take down the
metrics backend.

Alerts fire on symptoms visible to users, not on causes. Alerting on high CPU
produces pages nobody can act on; alerting on rising error rate produces pages
that matter.

Every alert links to a runbook. An alert without one is a page that wakes
somebody who then has to work out what to do from first principles.

## 10. Performance

Measure before optimising, and keep the measurement. An optimisation without a
before-and-after number is a guess that has been made permanent.

Do not add caching to fix a slow query. Fix the query. Caching a slow path hides
the problem until the cache is cold at the worst possible moment.

Batch outbound calls where the interface allows it. N+1 access patterns are the
most common performance defect and the easiest to spot in review.

Prefer streaming over accumulating for anything whose size is controlled by a
user. Reading an entire upload into memory works until somebody uploads a file
larger than the container's memory limit.

Background work has a concurrency limit. Unbounded parallelism turns a traffic
spike into a thundering herd against the database.

## 11. Frontend

Components receive data through props and do not fetch it themselves, except at
designated route-level containers. This keeps components testable and makes data
requirements visible.

Server state lives in the data-fetching layer, not mirrored into a global store.
Two copies of remote state will disagree, and reconciling them is work nobody
budgeted for.

Every interactive element is reachable and operable by keyboard, and carries an
accessible name. This is checked in review, not deferred to an audit.

Loading, empty and error states are designed and implemented for every view that
fetches. A view that only handles the success case will show a blank screen in
production.

Images specify dimensions so layout does not shift as they load.

Bundle size is budgeted. A new dependency that materially moves the budget needs
a reason recorded in the pull request.

## 12. Mobile

Screens render from local cache first and reconcile with the network afterwards.
A screen that cannot render without connectivity will feel broken on a train.

Background refresh respects system power policy. Aggressive polling is the
fastest way onto a user's battery-usage screen and then off their phone.

Deep links resolve to a valid state even on a cold start with no session.

Migrations of on-device storage are forward-only and defensive: a user may
upgrade from any previous version, not only the immediately preceding one.

## 13. Infrastructure

Infrastructure is provisioned from committed configuration. A resource created
by hand in a console is invisible to review and will be destroyed by the next
apply.

Every environment is created by the same code with different variables. An
environment that is special will be the one that breaks during an incident.

State is stored remotely with locking. Committing state files exposes secrets and
makes concurrent work impossible.

Container images are built from minimal bases, run as a non-root user, and
contain no build tooling. A shell in a production image is a convenience for an
attacker.

Resource limits are set on every workload. An unbounded container will consume a
node and take its neighbours with it.

Rollback is tested, not assumed. A deployment process whose rollback path has
never been exercised does not have one.

## 14. Code review

Pull requests are small enough to review in one sitting. A large pull request
receives a shallow review, which is worse than no review because it carries the
appearance of scrutiny.

The description explains why, not what. The diff shows what.

Review comments distinguish blocking objections from suggestions. Ambiguity here
wastes more time than any other review habit.

Nobody merges their own pull request without approval, including when the change
looks trivial. Most incidents come from changes that looked trivial.

Generated files and vendored dependencies are excluded from review by
configuration so that real changes are not buried.

## 15. Releases

Releases are cut from tags, and tags are immutable. A moved tag makes it
impossible to know what is deployed.

Every release has a changelog entry written for the people who use the software,
not derived mechanically from commit subjects.

Feature flags default to off, are checked in one place, and are removed once the
feature is fully rolled out. A flag that has been on for a year is dead code with
a runtime cost.

Database changes deploy separately from, and before, the code that requires
them. Deploying both at once means there is no safe rollback.

Post-incident reviews are blameless and produce specific actions with owners.
"Be more careful" is not an action.

## 16. Git workflow

Work happens on short-lived branches taken from `main`. A branch that lives
longer than a few days accumulates conflicts faster than it accumulates value.

Commit subjects are written in the imperative mood and explain the change, not
the file touched. "Fix rounding in refund totals" beats "update refunds.py".

Commit bodies explain why the change was made when the reason is not obvious
from the diff. The diff is always available; the reasoning usually is not.

Rebase to tidy a branch before review. Do not rebase a branch someone else has
based work on.

`main` is always releasable. A change that leaves `main` in a state that cannot
ship belongs behind a flag or on a branch.

Force-pushing to shared branches is prohibited. Force-pushing to your own review
branch is expected.

## 17. Dependency management

Adding a dependency is a decision with a maintenance cost, not a convenience.
Prefer the standard library, then a well-maintained dependency, then writing it.

Before adding a dependency, check its release cadence, its open issue count, its
licence, and how much of it you will actually use. A library used for one
function is usually a function.

Dependencies are pinned to exact versions in the lockfile, and the lockfile is
committed. Floating versions produce builds that differ between machines and
between days.

Upgrades happen in their own pull request, separate from feature work, so that a
regression can be bisected to the upgrade.

Transitive dependencies count. A small package with forty dependencies is not a
small package.

Licences are checked automatically. A copyleft licence entering a proprietary
codebase is a legal problem, not an engineering preference.

## 18. Documentation

Every service has a README that says what it does, how to run it locally, and
who owns it. These three facts answer most questions a newcomer has.

Documentation lives next to the code it describes and is updated in the same
pull request. Documentation in a separate system is documentation that will be
wrong within a quarter.

Architecture decisions that constrain future work are recorded with their
alternatives and the reason for the choice. A decision without its rejected
options cannot be revisited intelligently later.

Runbooks are written for someone woken at three in the morning: numbered steps,
exact commands, and the expected output of each.

Diagrams are generated from text where possible so they can be reviewed in a
diff and cannot drift silently from reality.

Do not document what the code says. Document what the code cannot say: why this
approach, what was tried before, what will break if it changes.

## 19. Data and privacy

Personal data is collected only where there is a stated purpose, and is deleted
when that purpose ends. "We might need it later" is not a purpose.

Data retention periods are defined per data category and enforced by an
automated job, not by intention.

Access to production data requires an approved, time-bound grant, and every
access is logged. Standing access for convenience is how a breach becomes a
catastrophe.

Exports containing personal data are encrypted at rest and expire. An unexpiring
link to a customer export will eventually be forwarded somewhere it should not
be.

Test and staging environments never contain real personal data. Synthesise it or
irreversibly anonymise it; partial masking has been defeated too many times to
be trusted.

Deletion requests propagate to backups, analytics stores and third-party
processors, not only to the primary database.

## 20. Third-party integrations

Every outbound integration is behind an interface owned by this codebase. Vendor
SDK types must not appear in domain code, so that replacing the vendor is a
contained change.

Webhooks from third parties are verified by signature before any processing, and
are processed idempotently because providers retry.

Third-party outages are expected. Every integration has a defined behaviour when
the provider is unavailable, and that behaviour is tested.

Credentials for third parties are scoped as narrowly as the provider allows. A
key that can do everything will eventually do something unintended.

Provider rate limits are respected proactively with a client-side limiter rather
than discovered through 429 responses in production.

## 21. Background jobs

Jobs are idempotent, because the queue guarantees at-least-once delivery and the
worker can die at any point.

Jobs are small and single-purpose. A job that does five things fails partway and
leaves the system in a state nobody designed.

Every job has a maximum attempt count and a dead-letter destination. Infinite
retry of a permanently failing job is a denial-of-service attack against your own
infrastructure.

Job payloads carry identifiers, not serialized objects. An object serialized at
enqueue time is stale by the time it runs.

Long jobs report progress and can be resumed. A six-hour job that must restart
from zero after a deploy will never finish during a busy week.

Scheduled work is defined in one place with an owner and an expected runtime.
Discovering a scheduled job during an incident is the wrong time to learn it
exists.

## 22. Search

Search indexes are rebuilt from the source of truth, and the rebuild is run
regularly enough to be trusted. An index that can only be repaired by hand will
drift.

Index updates are asynchronous and eventually consistent. The user interface says
so where the delay is visible.

Query parsing rejects input it cannot interpret rather than silently returning
everything. A search that returns the entire corpus on a syntax error looks like
a data leak.

Relevance changes are evaluated against a fixed query set before shipping.
Tuning relevance by impression produces improvements for the person tuning it and
regressions for everyone else.

## 23. Notifications

Notifications are deduplicated per user per event. A retry loop that sends the
same email eleven times damages trust more than the outage that caused it.

Every notification type has an unsubscribe path that works, and transactional
messages are separated from marketing messages at the transport level.

Templates are rendered with escaping on by default. Notification templates are a
common and overlooked injection surface.

Sending is asynchronous and failures are retried, but a permanent failure marks
the address rather than retrying forever.

Quiet hours are respected for anything that can wake a phone.

## 24. Experimentation

An experiment defines its metric, its minimum detectable effect and its duration
before it starts. Deciding when to stop after seeing the data produces results
that do not replicate.

Assignment is deterministic per user and stable across sessions. A user who sees
a different variant on each visit is not in an experiment, they are in a bug.

Experiments have an end date. Code carrying both branches indefinitely is a
maintenance cost paid forever for a decision nobody made.

Results are recorded with the analysis that produced them, including negative
results. An experiment log containing only wins is a marketing document.

## 25. Cost management

Cloud resources carry ownership tags. An untagged resource is one nobody will
turn off, because nobody can find out whether it matters.

Data egress and storage class are chosen deliberately. Egress is the line item
that surprises teams, and it is almost always avoidable by architecture.

Non-production environments shut down outside working hours unless there is a
reason for them not to.

Retention on logs and metrics is set per stream. Indefinite retention of debug
logs is usually the largest avoidable line on the bill.

Cost is reviewed monthly against the previous month, and unexplained growth is
investigated the way an error rate would be.

## 26. On-call

The on-call engineer's job during an incident is mitigation, not diagnosis.
Restore service first; understand it afterwards.

Escalation is expected rather than a sign of failure. An engineer who struggles
alone for two hours has made the incident longer, not shown resilience.

Every incident produces a written timeline within two working days, while
memories are accurate.

Handover between shifts includes anything currently degraded, anything recently
changed, and anything expected to change.

Pages that fire and are routinely ignored are deleted or fixed. An alert nobody
acts on trains everyone to ignore alerts that matter.

## 27. Configuration

Configuration is read once at startup and validated there. A malformed value
should stop the process immediately, not surface as a confusing failure during
the first request that happens to touch it.

Every setting has a documented default that is safe in production. A setting
whose default is unsafe will be wrong somewhere.

Configuration differs between environments only in values, never in shape. An
environment with extra settings is an environment nobody can reason about.

Feature behaviour is not configured through environment variables read deep in
the call stack. Pass configuration down explicitly so that it is visible in
signatures and testable without mutating the process environment.

Boolean settings are named for what enabling them does, and default to the
conservative option.

## 28. Time and scheduling

All timestamps are stored and compared in UTC, converted for display only at the
boundary the user sees.

Durations are stored as integers in a named unit rather than as an ambiguous
number. `timeout_seconds` cannot be misread; `timeout` can.

Never assume a day is twenty-four hours, a year is 365 days, or that time moves
forwards. Daylight-saving transitions and clock corrections both happen in
production.

Recurring schedules are defined in a named timezone, because "every day at
09:00" means something different in July than in January for most of the world.

Code that depends on the current time takes a clock as a parameter so that tests
can control it. Reaching for the system clock inside business logic makes the
behaviour untestable.

## 29. Caching

Every cache entry has an explicit expiry. A cache without one is a memory leak
with better public relations.

Cache keys include every input that changes the result, including the schema
version. A key that omits an input will serve one user another user's answer.

Caches are an optimisation, never a correctness mechanism. The system must
produce correct results with every cache empty.

Stampede protection is required on anything expensive. When a popular key
expires, a thousand simultaneous misses will do more damage than the cache ever
saved.

Negative results are cached deliberately or not at all. Accidentally caching "not
found" for an hour produces support tickets that are very hard to reproduce.

## 30. Events and messaging

Events describe something that happened, in the past tense, and are named for
the fact rather than the intended reaction. `order.cancelled`, not
`release_inventory`.

Event payloads carry identifiers and the minimum data needed to act. Consumers
fetch the rest, because a fat payload is a schema that every consumer is now
coupled to.

Event schemas are versioned and additive. Removing or repurposing a field breaks
consumers you do not know about.

Consumers are independent: one failing consumer must not prevent others from
processing the same event.

Ordering is not guaranteed unless the transport explicitly provides it, and
designs that require global ordering are usually designs that need rethinking.

## 31. Service boundaries

A service owns its data. No other service reads its tables, and no shared
database is a boundary.

A boundary that requires a synchronous call in both directions is not a
boundary. Either merge the services or redraw the line.

Services degrade independently. If service A is unavailable, service B returns a
reduced result rather than an error, wherever the product allows it.

New services are justified by a difference in scaling profile, ownership, or
release cadence — not by a desire for tidiness. Every service has a fixed
operational cost that a module does not.

## 32. Accessibility

Every interactive element is reachable by keyboard in a logical order, and the
focused element is visibly focused.

Colour is never the only carrier of meaning. Pair it with text, shape, or an
icon so the information survives colour blindness and greyscale printing.

Contrast ratios meet the published minimums for text and interface controls.
This is checked automatically rather than by eye.

Form inputs have associated labels. Placeholder text is not a label; it vanishes
exactly when the user needs it.

Dynamic updates announce themselves to assistive technology. A result count that
changes silently is invisible to a screen reader user.

Motion respects the reduced-motion preference, and nothing essential is conveyed
only through animation.

## 33. Internationalisation

User-facing strings are never concatenated from fragments. Sentence structure
differs between languages, and assembled sentences cannot be translated well.

Interpolated values carry named placeholders so translators can reorder them.

Plurals use the platform's plural rules rather than an English-shaped
`count === 1` check. Many languages have more than two plural forms.

Dates, numbers, currencies and names are formatted by locale-aware libraries.
Hand-rolled formatting is wrong for most of the world.

Layouts accommodate text expansion of at least a third, and are tested in a
right-to-left locale.

## 34. Technical debt

Debt is recorded where the code is, not in a separate backlog that nobody reads.
A short comment naming the shortcut and its consequence is more useful than a
ticket that will be closed unread in a year.

Deliberate shortcuts are labelled as deliberate, with what would need to be true
to justify fixing them. Undocumented shortcuts are indistinguishable from bugs.

Refactoring happens alongside feature work in the same area rather than as a
separate project. Standalone refactoring projects are the first thing cancelled
when priorities move.

Do not refactor code you are not otherwise touching, in a pull request that is
also changing behaviour. Separate the two so review can be meaningful.

## 35. Architectural principles

Prefer boring technology. Every novel component spends a portion of the team's
limited capacity for operational surprise.

Make the change easy, then make the easy change. If a modification is awkward,
the first commit reshapes the code and the second implements the behaviour.

Design for deletion. Code that can be removed cleanly is code that can be
changed cheaply, and most code is eventually removed.

Push complexity to the edges. A simple core with complicated adapters is easier
to reason about than the reverse.

Optimise for the reader. Code is read many times more often than it is written,
and the reader is usually someone with less context than the author had.

When two designs are close, choose the one that fails more obviously. Silent
wrongness costs far more than a loud crash.
